# 八千字从0到1讲清不一样的读书视频，制作角度对当前版本直接降维打击

![文章封面](assets/cover-5x2.png)

一本书讲了三分钟，观众却只记住一句“要做更好的自己”。这样的读书视频，你是不是也刷到过？

换一本书，还是那几句道理；换一个账号，还是同样的配音和素材。创作者忙着找金句、配画面、改字幕，做完以后自己也说不清：这条视频为什么值得别人看完，又为什么值得别人关注我？

我做这个项目，想解决的就是这件事。

设想一下：观众打开视频，先看到一个人被困在具体的处境里。他必须作出选择，选择引来后果，后果又把他推向下一步。画面跟着处境变化，旁白讲到转折，下一幅图才出现。视频结束，观众记住的是一个人的经历，也愿意回头看看那本书。

这就是 BV Workstation 想做的读书视频。它把图书资料、故事写作、人物视角、声音、连续画面和视频交付组织在同一个本地工作台里。我已经把项目开源，你可以照着部署，也可以让自己的 Agent 帮你完成安装和制作。

标题里的“降维打击”，说的是我想改变制作角度：从整理观点，转向组织故事。这是一种创作主张，不是对所有同类工具的性能排名。接下来不只展示效果，也把当前能做什么、要准备什么、怎么跑通，以及怎样判断它是否适合自己的内容业务，一起讲清楚。

项目地址：[kaiteJiang/book-video-workstation](https://github.com/kaiteJiang/book-video-workstation)。本文对应 2026 年 9 月整理的长篇故事与 AB 画面路线，具体命令以仓库当前帮助为准。

## 一、先决定观众为什么愿意留下来

我最在意的变化，是制作从哪里开始。

如果起点是“把这本书总结成五个知识点”，后面的工作很容易变成给知识点找插画。图漂亮了，声音顺了，视频仍然可能像一份会动的读书笔记。观众理解了结论，却没有参与事情的发展。

所以现在的流程先找一个值得讲透的核心故事：谁处在什么困境，冲突从哪里来，他采取了什么行动，为什么那个行动没有直接解决问题，最后付出了什么代价，或让事情发生了什么变化。

这些问题回答得越具体，稿件就越容易往前走。历史题材可以落到一项决策怎样改变人物命运；小说可以抓住一次求助、一次误会或一个迟到的答案；思想类图书则要找到有资料支撑的场景与讨论，不能为了戏剧性给作者编一段经历。

一本书有十个好观点，不代表一条视频必须塞十个。为了让一个故事成立，可以保留必要支线；与这条因果线无关的内容，宁可留到下一期。观众愿意看第二条，比第一条把所有内容讲完更有价值。

这个选择也会改变文稿的检查方式。我会问：删掉这一段，剧情有没有损失？如果没有，只是少了一次感叹，那就压缩。人物已经用行动表达了挣扎，旁白就不必再替他反复解释“我很痛苦”“我终于明白”。

## 二、同一本书，换一个有依据的讲述位置

很多人一听第一视角，就开始让主人公从头到尾说“我”。但第一视角真正有用的地方，是它限制了讲述者知道什么，也让观众暂时站到一个人的位置上。

这个项目不把主人公设成永远的默认答案。根据实际拿到的资料，叙述者可以是主人公、受害者、旁观者，或者在材料充分时采用反派视角。场景中有依据的物件也可以成为拟人化表达的载体，不过需要明确这是创作手法。

例如，一个宏大的历史冲突，从全知角度讲，很容易挤满时间、官职和名词。站在某个具体人物的位置，他首先要处理的可能是一封来信、一笔无法筹齐的钱，或者一项必须执行的命令。观众可以先理解他的局部处境，再逐渐看到更大的结构。

但视角不能成为编造的借口。人物当时不知道的事，不能突然从他嘴里说出来；史料没有记录的心理，也不能被包装成确定事实。原著引语、内容转述和创作者的解释，要能区分。

因此，文稿之外还要留一份来源与复查记录：用了哪些材料，哪些情节有支持，资料覆盖到哪里，为什么选这个讲述者。只拿到目录、划线和书评时，就说明这些材料的范围，不把它们说成已经读过整本书。

这套做法的卖点很实际：一个账号可以形成自己的观察角度，而不是每期换一本书、套一次同样的总结模板。可持续的辨识度，来自稳定的选择方式。

## 三、它是什么，又需要你参与到什么程度

BV Workstation 是面向 Windows 的本地视频生产工作台。Python 部分负责书籍身份、内容合同、状态、声音与字幕等环节；内置的 Remotion 渲染器负责画面组织；FFmpeg 和 FFprobe 参与音视频处理与检测。

你可以提供书名和作者，也可以提供自己有权使用的 TXT、PDF、EPUB 文件。标题作者模式先建立身份，再由 Agent 按实际可访问的渠道查证资料。文件模式也有自己的解析边界，扫描版 PDF、复杂排版或来源不足的书籍，不能假定都能直接变成可靠正文。

这里的 Agent，是能在项目目录里读文件、运行命令、调用所选工具，并理解生产规则的助手。当前项目更接近“你和 Agent 共用的制作工作间”，还没有包装成人人登录就能使用的网页平台。

你负责选题意图、关键审阅和最终判断，Agent 承担文件组织、流程执行、材料整理与重复检查。图片生成、微信读书访问等能力需要你自己的环境提供，克隆仓库不会自动附送这些服务。

尤其要说明，手绘视频后半段仍包含对话内编排。部分实际作品通过独立制作目录和交付清单恢复，这一步由 Agent 核对完成，不能宣传成 CLI 已经自动接管所有作品。知道这条边界，部署时就不会把“依赖安装完”误认为“全自动系统已经上线”。

## 四、连续画面怎么从“好看”走到“讲得清楚”

这套流程里，我认为最值得拆开的部分叫 AB 叙事。

一对画面中，A 表现一个故事小节开始时的处境，B 表现经历正文中的发展后，出现的高潮、结果或新困境。两张图之间必须有事情发生，有因果关系，有人物状态的变化。

它可以跨时间，也可以跨地点。一个人年轻时在某处作出选择，多年后在另一处承担后果，只要正文和资料支持，就可以构成同一小节里的发展。保持的是人物身份和故事连续性，不要求永远站在同一个机位、穿同一件衣服。

反过来，人物只是抬一下手、转一下头，文件从桌子左边挪到右边，这通常不够表达一个完整的故事变化。把同一张静帧多放几十秒，也不会自动增加剧情。

实际规划时，每组都要回答四个问题：A 时是什么处境；中间发生了什么；B 时改变了什么；这个变化怎样引出下一节。回答不出来，先回到稿件，不能让图片替空洞的文字虚构经历。

技术上，B 会引用当前 A 的路径和 SHA-256。可以把哈希理解成文件指纹：A 换了，系统就能识别原来 B 的参考关系可能已经过期。跨组还要维持人物身份与场景逻辑，避免前一张是青年、后一张突然变成另一个长相的人。

AB 的数量由故事语义决定，不按一句话配一张图，也不是每本书固定四对。正式旁白和语音识别提供实际时间轴，B 要在旁白讲到结果时出现。文字还在铺垫，画面就把结局揭晓，会直接削弱故事张力。

![三本历史作品配图的5:2三联展示](assets/history-triptych-5x2.png)

*历史配图三联展示：从左至右对应《南明史》《中国历代政治得失》《知行合一王阳明》。展示图由既有配图经 ImageGen 合版，用于呈现视觉方向，可能存在生成式合版差异，不作为逐像素原图或成片截图证明。三幅来自不同作品，不是一对 AB，也不表示它们属于同一个故事。*

这些画面展示的是当前一批作品采用的鲜彩漫画方向。项目也保留其他画风资产和旧模式，但选择画风应服务本篇故事。严肃历史、温和回忆和现代小说，没有必要为了所谓统一模板都长成同一种样子。

## 五、声音、字幕和转场，为什么要一起考虑

长篇故事不是把短视频的语速维持八分钟。观众要跟上人物关系、地点变化和选择后果，声音是否耐听、停顿是否自然，会不断影响理解。

当前长篇路线从豆包音色候选池按故事筛选，最多先选三种，用同一段已批准正文试听。选段可以在中间，不一定是开头，但必须包含足以判断叙述和情绪变化的内容。

音色目录里存在某个名称和 ID，和自己的账户可以调用，是两件事；账户能调用，和听起来适合这篇稿，又是两件事。项目会区分这些状态，避免一张候选清单被误写成已经实测通过的推荐榜。

确定声音后，当前约定以 TTS 的 `speed=1.12` 生成正式配音，不再靠后期加速硬压时长。新音频的真实长度决定时间轴。六到八分钟是常用预算，十分钟是审阅提醒，故事四分钟讲完就四分钟，不需要注水凑长篇。

字幕同样要跟着实际音频走。先为批准正文准备按口语语义断开的字幕文本，再对齐 ASR。不能让模型识别错了一个年份，字幕就跟着错；也不能为了排版顺手改掉已批准正文，却继续沿用旧批准。

转场也承担叙事任务。当前 AB 路线使用墨迹展开表达组内变化，组间用交叉溶解连接；合同中的典型时长分别是四十五帧和十五帧。它们不是越炫越好，关键是画面出现的时机和旁白讲述的内容一致。

## 六、为什么我宁愿让流程在关键处停下来

做一条视频最浪费的情况，是稿件方向错了，却已经生成十几张图、合成完整音频，最后才发现整个故事讲歪了。

所以项目把确认放在最有价值的节点：先完整文稿，再声音试听，再开头、关键中段和结尾的三对代表图，最后补齐、渲染、检查。代表图检查的不是“有六张图片”，而是人物是否连续、画风是否合适、叙事跨度是否成立。

这些确认绑定的是具体候选和文件指纹。改了文稿，就不能让旧批准悄悄继续生效；换了参考图，也要检查相关画面和清单。对于长期制作，这比记住一句“上次好像说可以”可靠得多。

不过，流程不会把重复询问当成认真。用户已经明确授权某篇作品接下来的制作阶段，就在这次授权范围内推进。它要保存的是清楚的责任和状态，而不是制造无休止的确认按钮。

这是项目与一堆临时脚本的区别：你能够知道目前在哪里、为什么停下、批准了哪一份、下一步会产生什么。这些能力在第一次制作时不显眼，到第五条、第十条需要修改旧作品时，会明显减少混乱。

## 七、从零部署：先把本地工具准备好

下面按 Windows 路线来。当前 Python 项目要求 3.11，渲染器要求 Node.js 至少 20，还需要 Git、uv、npm、FFmpeg 和 FFprobe。不要一看到 AI 视频，就先去买显卡；是否需要本地 GPU，取决于你是否选择本地模型路线。

uv 可以按[官方安装说明](https://docs.astral.sh/uv/getting-started/installation/)安装；Windows 用户也可以使用官方文档列出的包管理器命令。FFmpeg 可从[官方下载入口](https://ffmpeg.org/download.html)查找 Windows 构建。安装完成后，重新打开 PowerShell，让新的路径生效。

先做几项简单检查：

```powershell
git --version
uv --version
node --version
npm --version
ffmpeg -version
ffprobe -version
```

找不到命令通常说明安装或 PATH 配置还没完成。FFmpeg 也可以在项目配置里写绝对路径，不必为了适应别人的目录结构，把自己的电脑弄成同样的盘符布局。

然后克隆并安装项目：

```powershell
git clone https://github.com/kaiteJiang/book-video-workstation.git
Set-Location book-video-workstation
uv python install 3.11
uv sync --group dev
Push-Location vendor/story_to_handdrawn_video
npm ci
npm run check
Pop-Location
```

Python 和 Node 是两套依赖，前面的 `uv sync` 不会替你安装渲染器需要的 npm 包。使用仓库锁文件安装，可以减少“我这台机器和作者那台机器版本不同”的问题。

安装过程中会下载依赖；渲染所需浏览器也可能需要另外准备或下载。第一次启动慢，不一定是项目没有响应。先看具体日志停在依赖下载、浏览器启动还是编码，再决定怎样处理。

## 八、配置自己的路径和服务

回到项目根目录，建立本地配置：

```powershell
Copy-Item config.example.yaml config.yaml
uv run bv --help
uv run bv doctor
```

已有 `config.yaml` 时保留自己的配置，不要反复用示例覆盖。示例里的 FFmpeg、FFprobe、字体和本地模型目录只是路径样例，需要换成你的实际位置。YAML 对缩进敏感，修改时不要混用制表符与空格。

当前长篇声音路线使用豆包 TTS 和火山 ASR。代码通过环境变量名称读取凭据，例如 `BV_DOUBAO_TTS_API_KEY`、`BV_VOLC_ASR_API_KEY`。ASR 还支持配置中列出的 App Key、Access Key 名称，具体使用哪种凭据要匹配自己的服务开通方式和代码接口。

建议在本机的环境变量设置里填写真实值，重新启动需要读取它们的终端或 Agent。不要把密钥粘到公开 Issue、演示截图和仓库配置中，也不要要求 Agent 把完整环境变量列表打印出来证明“配置成功”。

`bv doctor` 默认做本机检查；`--live` 会涉及真实模型或云服务探测，二者不能混用。当前 doctor 还包含历史 IndexTTS2 路线的检查项，选择豆包的用户看到本地模型缺失时，应由 Agent 结合所选路线判断，不能据此认定必须再部署一套本地 TTS。

同样，配置示例里的短视频时长不代表新故事也受几十秒限制。长篇要走 story 导入及对应的 Episode profile。只把某个全局数字改成八分钟，并没有完成内容模式和生产状态的切换。

本地优先意味着文件和状态主要留在自己的电脑；使用云 TTS、ASR 或生图时，相应文本、音频或参考图仍会发送到所选服务。这一点要在选择路线时理解清楚。

### 第一次部署最容易卡住的几个地方

如果 `uv sync` 报 Python 版本不满足，先核对项目要求的是 3.11，而不是电脑里“已经有一个 Python”。同一台电脑可以有多个版本，让 uv 为这个项目选择正确版本，比卸载其他软件正在用的 Python 更稳妥。

如果 npm 安装成功，渲染仍然失败，先确认命令运行在内置渲染器目录。缺包、浏览器无法启动、素材路径不存在和视频编码失败，是不同问题，处理方式也不同。不要看到一个失败，就把整套依赖全部升级到最新版；先保留日志里最早出现的有效错误。

如果画面有了，字幕却变成方框或宽度异常，检查字体路径、字体家族和中文字体是否可用。把别人的 Windows 字体路径照抄到自己的环境，并不能保证渲染结果一致。字幕要在最终视频里检查，单独打开文本文件看不出实际排版问题。

如果服务返回鉴权失败，检查变量名、当前进程是否重新读取环境、账户是否开通对应资源。不要在错误尚未定位时不断重复提交正式任务。尤其是已经创建的长文本合成任务，要先查询原任务状态，避免把恢复操作变成重复消费。

如果新故事突然被按几十秒检查，优先看 Episode 的生产配置和导入方式，确认是否进入 story 路线。不要只改成片检测阈值来让检查通过，那样可能把错误的制作配置藏起来。

第一条视频跑通以后，记录自己的工具路径、所用版本和实际成功的服务配置名称。下次迁移电脑时，依据这份记录重建环境；密钥仍单独管理。部署的目标是得到一个能复现的工作环境，而不只是今天碰巧成功一次。

## 九、让 Agent 接手第一本书

环境准备完，先让 Agent 读取 `AGENTS.md`、`README.md`、长篇生产手册，以及仓库内的三个生产 Skill。不要假定安装在个人技能目录里的旧副本，永远与当前仓库同步。

新建书籍身份可以使用：

```powershell
uv run bv new --title "你的书名" --author "作者姓名"
```

有合法可读的文件时，可以把路径作为参数：

```powershell
uv run bv new .\my-book.txt --title "你的书名" --author "作者姓名"
```

保存命令返回的 `book_id`，然后用状态命令查看：

```powershell
uv run bv status --book-id <book_id>
```

尖括号内容要替换成实际值。这里不让新手紧接着运行 `bv next`，因为它会推进生产，不是单纯查状态，而且新故事不应该误入旧的 value 起稿路线。

你可以把下面这段直接交给 Agent：

> 请按仓库当前长篇故事路线制作这本书。先核对书名、作者和实际可用资料，选择一个值得讲透的核心故事，并说明叙述视角、认知边界及资料覆盖范围。文稿用事件、冲突、应对和结果推进，不编造人物心理，不使用去 AI 味 Skill。先交完整正文、事实复查和故事小节计划给我，停在文稿待审。文稿批准后，再按当前授权安排音色试听、代表 AB 图、完整制作与检查。不要上传平台。

微信读书是目前实际创作中使用的来源渠道之一，但它需要你自己的合法访问环境。找不到书、作者不匹配、资料不足或接口失败，都应该如实记录。不能为了让流程看起来自动，就把猜出来的情节写进去。

如果你提供的是已经定稿、且明确授权直接制作的正文，Agent 应保留原文，在对应范围内执行。需要实质修改事实时，先把修改呈现出来。项目不能拿其他作品的批准记录来替这篇稿盖章。

## 十、候选导入以后，怎样走到一条成片

新故事写完后，Agent 要把正文、元数据、证据、段落跨度和事实复查整理成项目能验证的格式。仓库提供导入入口：

```powershell
uv run bv import-story --help
uv run bv import-story <book_id> <episode_id> .\story.txt .\story-contract.json
```

这两份文件需要根据当前 schema 准备，不是随便保存一个文本和空 JSON 就能通过。导入只登记候选，状态会停在 `awaiting_script_review`，不会因此自动获批。

看完当前完整稿件并决定通过后，才使用：

```powershell
uv run bv approve <book_id> <episode_id> script
uv run bv voice-pool --help
```

后续由 Agent 按手册执行声音筛选、实际试听、正式旁白、ASR、字幕和 AB 画面。先检查三对代表图，能较早发现人物不一致、剧情跨度不足、颜色不适合这本书等问题；确认后再补齐其余画面。

默认成片采用 1080×1920、30fps 的竖屏规格，独立视频封面采用 3:4。本文的 5:2 横版封面与三联图服务于分享文章，不改变视频本身的画幅合同。

已有作品恢复时，先检查 `current_production.json` 指向哪一个制作目录，再核对那个目录里的 `delivery.json` 和真实文件指纹。不要因为另一个旧目录里有一份 MP4，就把它当成最新版本，更不要为了“继续”而重新生成已经确认过的所有素材。

最终给使用者的目录非常简单：`成品/<书籍编号>+<书名>+<日期>/`，里面只有 `成品视频.mp4` 和 `封面图.png`。内部仍保存来源、文稿、音频、字幕、AB 图与检查记录。没有自己的选题池时，需要先明确编号映射，不能随便借用别人的书籍编号。

## 十一、怎么判断这次真的完成了

我不把终端显示“成功”当成最后结论。视频可能存在却打不开，也可能能播放但少一句旁白；字幕可能全部生成，却在人名、年份或换行处出了问题。

技术检查会关注文件存在与哈希、音视频规格、实际时长、全片解码、字幕与正文一致性、时间轴覆盖，以及画面引用关系。对创作者而言，还要看开头能不能进入故事，关键变化有没有提前泄漏，人物长相是否连续，结尾有没有回应最初的问题。

这两类检查互相补充。测试通过，说明相应代码路径符合测试预期；关键帧检查，说明看过那些采样位置；它们都不能被写成“已经有人完整看完并满意”。

当前作品清单也区分“可以交给用户观看”与“用户最终验收”。这种区分看起来细，其实很适合协作：接手的人不需要猜哪些环节做过，哪些还需要自己看。

开发者可以运行 `uv run python -X utf8 -m pytest -q`，在渲染器目录运行 `npm run check`。其中真实本地渲染测试会比普通单元测试慢；测试使用本地 fixture，不应为了跑测试消耗付费媒体服务额度。

遇到问题时，提交书籍 ID、所在阶段、脱敏错误和复现步骤，比贴一整屏私人资料更有效。修复后从明确的停点恢复，也是这套工作台的重要价值。

## 十二、吸粉潜力，具体可能来自哪里

先说判断：它有帮助创作者做出辨识度的可能，但仓库本身不能保证流量。当前展示的是生产能力与作品方向，没有拿经过验证的涨粉数据来证明它必然优于其他形式。

我更看好四个可以实际验证的方向。第一个是进入门槛。观众未必愿意听一段抽象观点，却可能愿意看一个人怎样处理困境。故事给了他一个跟下去的理由。

第二个是系列感。同一账号持续用某种观察方式讲书，例如“站在失败者的位置重新看选择”，观众关注的对象就可能从某一本书，转为你的讲述方式。这里真正要统一的是选题和判断，画面只是帮助形成识别。

第三个是讨论空间。人物做了一个有代价的决定，评论区就有了具体问题：你会不会这样选？你认为哪一步还存在别的可能？这种讨论比在结尾硬问一句“你怎么看”更自然，但也要允许观众提出不同解释。

第四个是跨内容承接。一条视频可以对应一篇讲来源与制作方法的长文，再沉淀成一个主题合集。对故事感兴趣的人继续看书，对制作感兴趣的人阅读项目文档，两类读者都能找到下一步。

验证时不要只看播放量。可以记录开头留存、平均观看时长、完成观看情况、收藏、有效评论和关注转化。平台提供什么数据就记录什么；不同长度的视频，要结合时长比较，不能只拿一个百分比下结论。

第一轮先做一个主题的小系列，尽量保持画风和制作条件相近，集中调整选题与开头。每条同时改十个因素，即使数据变好了，也很难知道下一条应该延续什么。这里说的是运营试验思路，项目并不内置平台数据后台。

## 十三、变现可以往哪里走，先卖什么更合理

开源以后，代码谁都能拿到。真正有机会形成收入的部分，是你能否把它变成稳定、清楚、有人需要的交付。

一个方向是内容账号。持续做某个领域的读书故事，积累信任后，再探索与读者需求匹配的图书推荐、读书活动或内容合作。合作方式与平台要求需要在实际开展时核对，这里没有承诺任何佣金比例或收益水平。

另一个方向是制作服务。书店、阅读社群、出版相关团队，可能需要把一段材料变成能看完的视频。对方买的是选题理解、叙事能力、视觉一致性、修改响应和交付可靠性，不会因为你有一个脚本就自动下单。

这类服务应该先讲清楚范围：谁提供来源，谁负责事实确认，成片多长，包含几轮修改，交付哪些文件，是否需要不同画幅。把修改边界写清，比先报一个看起来很低的价格更能保护交付质量。

还有部署与培训方向。有人愿意自己做内容，只是不想从 Python、Node、字幕字体和环境变量开始摸索。你可以提供环境配置、第一条作品陪跑、流程诊断或团队使用培训，收费对应明确的服务结果，并让对方知道项目本身可以免费取得。

进一步的产品化，也可以围绕多人协作、素材管理、任务排队和审核界面展开。但这些属于未来可开发的方向，当前仓库没有因此自动具备团队 SaaS、支付系统或多租户账户能力。

算成本时，至少把资料整理、文稿修改、TTS、ASR、生图重试、渲染、人工审阅和售后修改放进去。一次生成的服务费只是其中一部分。连续做三条，记录真实时间与调用次数，再讨论报价，会比引用一个脱离自己流程的“单条成本”更可靠。

## 十四、开源部署之后，哪些事仍然需要自己做好

项目主体采用 MIT 许可证，内置组件、字体和依赖保留各自条款，具体见仓库的 `LICENSE` 与 `THIRD_PARTY_NOTICES.md`。涉及 Remotion 的商业使用，还应查看[官方许可说明](https://www.remotion.dev/docs/license)，不要把项目主体的 MIT 标签理解为所有依赖都没有额外条件。

同样，拿到代码不等于取得任意书籍内容、第三方音色或图片的使用授权。最直接的做法，是从你能合法使用、资料清楚、确实理解的内容开始，让每一步的依据都能说得明白。

公开仓库保存代码、规则、文档和经过选择的演示素材；电子书、私人笔记、原始服务回执、密钥和完整生产目录留在本地。更新代码时也要维持这个边界，不能为了同步方便，把整个工作区打包上传。

目前它仍需要有判断力的创作者参与，也需要一个能认真读规则、执行工具的 Agent。环境适配、来源不足、声音不合适、某幅图不连贯，都可能让一次制作停下来。这些问题需要解决，不能用“AI 全自动”四个字抹过去。

如果你第一次尝试，我建议把目标缩小到一条：选一本熟悉的书，挑一个讲得完整的故事，认真看完文稿，认真听一段声音，认真比较三对画面。先建立自己对好作品的判断，再扩大产量。

我把这个项目开源，是希望这些已经整理成规则和代码的经验，能变成更多人可以继续改进的起点。你可以贡献一个可复现的错误、一处更清楚的文档，或者一个经过实际制作检验的改进，而不必先写出很大的功能。

如果你也想做一种让人记住人物、愿意追问选择、最终重新走近一本书的读书视频，就从自己的第一个故事开始。仓库和部署方法都在这里，下一条片子的叙述角度，可以由你来决定。
