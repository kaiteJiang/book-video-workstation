# BV_Workstation 豆包长篇图书视频与日期交付设计

## 1. 决策状态

- 日期：2026-08-23
- 用户批准：方案 A
- 首个真实节目：余华《活着》E001
- 本规格只扩展现有手绘视频流水线，不新增 CMD、网页、GUI 或自动发布功能。
- 现有《我与地坛》及其已批准产物保持不变。

## 2. 目标

在不破坏现有 45–60 秒 IndexTTS2 流程的前提下，增加三个可复用能力：

1. 每个 Episode 可以选择 `indextts2` 或 `doubao` 作为旁白提供方。
2. 每个 Episode 可以用独立生产配置控制正式成片时长。《活着》使用 120–150 秒，目标约 135 秒。
3. 技术流水线继续使用稳定的规范文件名，经过 QC 的交付物另按北京时间日期导出，重复导出不覆盖旧版本。

成功标准是用《活着》真实跑通一条 120–150 秒视频，获得用户最终批准，并留下可用于下一本书的文件合同、测试和故障记录。

## 3. 内容设计

### 3.1 视频主题

视频解释整本《活着》给读者带来的价值。它不做单一观点扩写，不做情节流水账，也不把人物死亡数量当作传播噱头。

核心判断是：人在努力无法保证结果、生活不断失控的时候，仍然可以重新看见身边的人，把今天过完。文稿不赞美苦难，不承诺读书可以疗愈现实问题，也不写“坚持就会成功”。

### 3.2 目标受众与痛点

主要受众是正承受现实压力的成年读者，尤其包括：

- 家庭责任、收入和工作压力叠在一起的人；
- 经历亲人离世、关系结束、健康变化或生活失序的人；
- 付出很久仍未得到预期结果，开始怀疑努力意义的人；
- 知道许多道理，却仍不知道怎样面对具体一天的人。

文稿只把这些处境写成明确的第二人称假设，不虚构读者来信、朋友经历或作者亲历。

### 3.3 叙事结构

正式口播以最终音频时长为准，目标 135 秒，允许范围 120–150 秒。建议结构如下：

| 时段 | 内容任务 | 比例 |
|---|---|---:|
| 0–25 秒 | 从现实生活中的失控感进入 | 约 18% |
| 25–75 秒 | 用必要情节概括福贵的人生变化 | 约 37% |
| 75–125 秒 | 解释全书给当代读者的理解和变化 | 约 37% |
| 125–150 秒 | 回到读者生活并自然推荐原书 | 约 8% |

现实生活联系约占文稿意义单元的 60%，原著人物和情节约占 40%。比例不是机械字数配额，任何事实归因仍须服从研究证据。

文稿使用 `human-writing` 审校。不得伪造原句、页码、人物心理或精确历史细节；事实、解释和为插画构造的象征画面必须分开。

## 4. 单期生产配置

每个 Episode 根目录新增 `production_profile.json`。它是本期媒体参数的唯一持久来源，必须参与 TTS、分镜、渲染、QC 和交付 StageManifest 的输入哈希。

《活着》初始配置：

```json
{
  "schema_version": 1,
  "duration": {
    "hard_min_seconds": 120.0,
    "ideal_min_seconds": 128.0,
    "ideal_max_seconds": 142.0,
    "hard_max_seconds": 150.0
  },
  "tts": {
    "provider": "doubao",
    "resource_id": "seed-tts-2.0",
    "voice_type": null,
    "speed": 1.0
  },
  "visual": {
    "seconds_per_scene_min": 7.0,
    "seconds_per_scene_max": 11.0,
    "representative_count": 3,
    "transition": "cross-dissolve"
  },
  "delivery": {
    "timezone": "Asia/Shanghai",
    "include": ["video", "cover", "script", "voice", "subtitles", "manifest"]
  }
}
```

`voice_type` 在试听批准前必须为 `null`。试听批准后写入准确音色 ID 并生成新配置哈希。修改时长、Provider、音色或语速都会使下游音频和画面清单失效。

旧 Episode 没有此文件时继续使用现有 45–60 秒和 IndexTTS2 黑金3默认值，保证向后兼容。

## 5. TTS Provider 边界

### 5.1 公共接口

`TtsStage` 不再直接判断“黑金3”，而是调用统一的 `NarrationSynthesizer`：

```text
synthesize(approved_script, production_profile, authorization)
    -> raw_audio + provider_receipt
```

两个实现：

- `IndexTTS2NarrationSynthesizer`：复用现有本地推理和参考音频校验。
- `DoubaoNarrationSynthesizer`：调用火山引擎豆包语音长文本接口，下载一次完整合成结果。

Provider 输出都必须交给现有本地 `build_voice_master()`，统一生成 48 kHz、单声道 PCM `voice_master.wav`，随后火山 ASR 仍是字幕时间轴的权威来源。

### 5.2 豆包音色试听门

正式合成前，只从当前账号已经开通、并且明确支持同一异步长文本服务的有声阅读音色中选择最多三个候选。不得从豆包通用大模型音色总表中挑选一个长文本接口不支持的音色。三个候选使用同一段 15–25 秒批准文稿，语速相同，不加背景音乐。

试听产物保存到：

```text
episodes/E001/.private/candidates/tts-audition-YYYYMMDD/
├─ candidate-01.wav
├─ candidate-02.wav
├─ candidate-03.wav
└─ audition-manifest.json
```

用户批准后，记录 Provider、`voice_type`、语速、试听文稿 SHA-256 和批准音频 SHA-256。未经批准不得提交完整长文本任务。

### 5.3 长文本调用

- 使用异步长文本合成的提交和查询流程；不配置公网回调。
- 一次正式旁白最多提交一个任务。
- 默认不自动重试，不自动改音色，不回退 IndexTTS2。
- 查询超时、服务未开通、音色无权限或下载失败时，保留脱敏回执并停在 `tts_failed`。
- 只有用户重新批准具体重试或改用黑金3后，才可发起新的正式任务。
- Provider 字词时间戳可保存为辅助证据，但不能替代最终 WAV 的火山 ASR 对齐。

### 5.4 凭据与隐私

新增环境变量名：

```text
BV_DOUBAO_TTS_API_KEY
```

程序通过 `x-api-key` 请求头调用，且只报告 `SET` 或 `UNSET`。API Key、完整 Provider 响应和下载地址不得出现在终端输出、仓库、公开清单或对话中。现有 ASR 凭据不得假设为已经开通 TTS。

外部调用继续受 `RuntimeAuthorization(allow_external=True)` 控制。授权记录绑定书籍、Episode、文稿 SHA-256、音色 ID、最大试听请求数、最大正式任务数和零回退规则。

## 6. VoiceManifest 兼容升级

VoiceManifest 增加：

```text
provider: indextts2 | doubao
provider_voice_id: string
provider_receipt_sha256: string | null
```

`reference_sha256` 改为可空：IndexTTS2 必须非空，豆包必须为空。旧清单缺少 `provider` 时按 `indextts2` 迁移，仍按原规则验证黑金3参考音频。

Provider回执只保留必要的任务标识摘要、状态、输入哈希和响应哈希。任何下载 URL、Token 或原始错误正文都不得进入公开 VoiceManifest。

## 7. 时长与画面扩展

### 7.1 时长策略

技术样片仍使用 10–20 秒策略，并且只能截取正式批准文稿和正式音色试听中的连续片段。

正式模式从 `production_profile.json` 读取 120–150 秒策略。`build_voice_master()` 不再依赖写死的 `FULL_EPISODE_POLICY`。音频短于 120 秒或长于 150 秒均失败，不通过强制大幅变速塞进范围；最大自动语速修正仍限制在 1.08 倍。

### 7.2 插画密度

按最终 WAV 时长和 7–11 秒/场计算场景数，120–150 秒通常得到 12–21 个场景。系统不写死 18 张图片。

仍然只先生成开头、中段、结尾三张代表插画。代表图批准后才生成剩余图片。视觉设计约 60% 使用当代生活场景，约 40% 使用福贵、乡土生活和克制的象征场景；现代读者与福贵使用不同角色标识，不能混成同一个真实人物。

画风保持低饱和中国乡土手绘、水彩和铅笔线稿倾向。不得复刻电影演员脸、生成假书封、在画内写书名或把苦难画成猎奇场面。

### 7.3 渲染和QC

- 1080×1920、30 fps、H.264、`yuv420p`。
- 15 帧交叉叠化，转场中不出现纸白空场。
- 单行无标点字幕，继续使用 Microsoft YaHei 粗体和半透明深色底框。
- AAC、48 kHz、双声道；最终音画误差不超过一帧。
- QC 使用本期生产配置验证 120–150 秒，不影响旧 Episode。
- 技术QC不代替人物一致性、情绪、审美和平台政策人工检查。

## 8. 日期化交付

流水线内部继续使用稳定路径，例如 `media/final/final.mp4`。通过最终技术 QC 后，新增 `DeliveryExporter`，把用户需要的文件复制到：

```text
episodes/E001/deliveries/YYYY-MM-DD/
├─ YYYY-MM-DD-活着-成片.mp4
├─ YYYY-MM-DD-活着-作品封面.png
├─ YYYY-MM-DD-活着-文稿.txt
├─ YYYY-MM-DD-活着-旁白.wav
├─ YYYY-MM-DD-活着-字幕.ass
├─ YYYY-MM-DD-活着-交付清单.json
└─ YYYY-MM-DD-活着-批准记录.json  # 最终批准后才出现
```

日期使用 `Asia/Shanghai` 的实际导出日期。书名先经过 Windows 文件名安全化处理，但交付清单保留原始书名。

同一天目标目录已有任意同名交付物时，整套文件共同升级为 `-V2`、`-V3`，不能只给单个文件加版本。导出先写入同目录临时目录，逐项核对源文件和副本 SHA-256，再原子发布整套交付物。现有文件、符号链接、junction 或其他重解析目标一律拒绝覆盖。

交付清单记录：

- 书名、作者、book_id、episode_id；
- 导出日期、版本、时区；
- 批准文稿和生产配置 SHA-256；
- TTS Provider和音色 ID，不含凭据；
- 每个交付文件的相对路径、字节数和 SHA-256；
- final.render.json 和 final.qc.json 的 SHA-256；
- 导出时的审核状态，固定为 `awaiting_final_review`。

用户批准成片后，不修改或覆盖上述交付清单，而是原子新增批准记录。批准记录绑定交付清单 SHA-256、成片 SHA-256、作品封面 SHA-256、批准日期和批准后的 `final_approved` 状态。若成片被拒绝并重新生成，新的整套交付物使用下一版本号，旧交付包和旧审核结果保持不变。

独立作品封面保持 1080×1920，标题“活着”居中放大。它不作为商品书封烧入 MP4，也不再由代表插画机械裁切。

封面使用本机 `punk-cover` Skill 的受控工作流单独制作：只从已批准文稿、语义锁和本期生产配置提炼标题、1–3 句语境摘要、目标读者、情绪、单一视觉隐喻与禁用元素；只选择一个 `outputs` 包含 `cover` 或 `poster` 的风格，并按该风格的 `META.md`、`STYLE.md` 与 `cover-prompt-blueprint.md` 编译成一份完整提示词。不得把原文或整篇文稿复制进提示词，不得混搭多个风格，也不得用假书封、影视演员脸、苦难奇观或营销广告画面代替书的内涵。

本期《活着》默认自动选择 `french-minimal-ink-poster`（法式极简墨线海报），因为它能以克制墨线、大留白和一个准确隐喻承载“生活不断失去之后，人如何继续把日子过下去”的整体价值。最终隐喻、副标题和画面主体必须在文稿批准后重新从批准稿推导，不能把这句说明直接当成成品文案。完整提示词保存在 `punk-assets/punk-cover/huo-zhe-e001/prompts/cover.md`；只有图像生成工具返回本次调用的明确文件路径、可下载地址或图像字节时，才接收本次封面资产，禁止扫描宽泛生成目录猜测产物。

封面外部生成仍属于大阶段授权门。生成后的原图须经本地 9:16 规范化、1080×1920 尺寸检查、SHA-256 绑定和标题人工核对；标题错字、缺字、裁切、风格不符或隐喻偏离均不得进入交付包。封面清单绑定批准文稿、语义锁、生产配置、完整提示词、唯一风格 ID、原始生成资产和规范化输出的哈希。最终封面与成片一起进入第四道人审门。

## 9. 状态与审批门

保留现有四道人工门：

1. 文稿批准。
2. 音色试听批准和“开始制作”外部调用授权。
3. 开头、中段、结尾代表插画批准。
4. 完整视频和独立封面最终批准。

新增状态或等价持久证据：

```text
awaiting_voice_audition_review
voice_profile_approved
delivery_ready
```

候选交付导出发生在技术 QC 后，供用户直接观看日期命名的成片和封面。用户批准后只新增不可覆盖的批准记录，不修改已经发布的交付清单或媒体文件。

## 10. 错误处理与恢复

- 已提交的豆包任务必须保存脱敏回执，重启后先查询原任务，不能直接重复提交。
- 音色、文稿、语速或Provider变化时，旧试听和旧旁白移入当前 Episode 的 `.private/history/<timestamp-purpose>`。
- 120–150 秒合成失败不能伪装成成片失败，也不能拿试听音频代替正式旁白。
- 日期交付失败不改变已通过 QC 的内部成片；修复后重新导出下一版本。
- 任一哈希不一致时停在当前门，不覆盖旧文件。
- 不自动上传抖音、视频号或小红书。

## 11. 测试策略

### 11.1 单元测试

- 旧 Episode 无生产配置时仍使用 45–60 秒和 IndexTTS2。
- 《活着》生产配置接受 120–150 秒，119.9 秒和 150.1 秒失败。
- `TtsStage` 根据Provider路由，不再把黑金3约束施加到豆包。
- VoiceManifest旧格式迁移与两个Provider互斥字段校验。
- 豆包请求体、鉴权Header和错误输出脱敏。
- 一个正式授权只允许一次正式提交，查询不计作重复提交。
- Provider失败不自动重试、不自动回退。
- DeliveryExporter按北京时间命名、整套升级V2并拒绝重解析目标。
- 导出副本与源文件哈希逐项相同。

### 11.2 集成测试

- 用假豆包服务跑通试听、批准、完整旁白、火山ASR替身、字幕、分镜、渲染、QC和日期交付。
- 用约 135 秒夹具验证 Remotion、FFmpeg、字幕末尾和转场时码。
- 验证修改生产配置后所有依赖 StageManifest 变为 stale。
- 验证旧《我与地坛》仍能读取、查询状态和通过现有清单校验。

### 11.3 真实验收

1. 确认豆包TTS凭据仅显示 SET/UNSET，并确认账号实际开通可用音色。
2. 经一次明确授权生成最多三条短试听。
3. 用户批准一个音色后，经一次明确授权提交一条完整旁白。
4. 完整 WAV 通过时长、听感、响度和火山ASR文本一致性检查。
5. 三张代表插画批准后生成剩余插画。
6. 真实生成 120–150 秒视频、独立封面和日期候选交付包。
7. 用户观看并批准最终成片，随后生成绑定交付清单和媒体哈希的批准记录。

## 12. 明确不做

- 不删除或替换 IndexTTS2。
- 不把所有新书默认改成 120–150 秒。
- 不使用豆包客户端界面录音或手工抓取音频冒充API自动化。
- 不在本次增加BGM、网页、GUI、CMD入口或平台自动发布。
- 不在文稿批准前调用TTS、ASR或图片生成。
- 不为了更长时长预生成第二、第三主题。

## 13. 实施顺序

1. 生产配置与动态时长策略。
2. TTS Provider接口和VoiceManifest向后兼容。
3. 豆包异步长文本客户端、授权和脱敏回执。
4. 音色试听审批门。
5. 长时长分镜密度与QC适配。
6. 日期化DeliveryExporter。
7. 单元与集成测试。
8. 更新生产手册和 `producing-book-handdrawn-videos` Skill。
9. 用《活着》完成真实端到端验收并记录错误修复。
